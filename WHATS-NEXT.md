### 1. Second visual primitive — spatial-relation filter (or presence-over-time / dwell op)

- **Why now:** #52 proved the full-stack primitive pattern end-to-end (new binding kind + cache slice + answer branch + UI step-kind + eval cell), `CLAUDE.md` names this as *the* growth axis, and #61 just built the gallery that *displays* breadth — every new primitive now makes the front door richer for free. The cleanest next primitive is one of the two **layer-2-only** candidates the #52 plan named as alternatives: a **spatial-relation filter** (local geometry over existing detection boxes — "left of", "near", "above", "between") or a **presence-over-time / dwell op** (aggregates detections across sampled frames into a duration). Both answer genuinely new question shapes the 9-op surface can't ("is the keeper left of the ball?", "how long is #7 on screen?"), and crucially both are **deterministic and external-dependency-free** — no Azure visual feature, no TPM quota, no paid live re-capture, and the eval cell scores exactly (not `any_grounded`). That sidesteps the two pain points #52 hit (the ~$0.40 capture step and the non-deterministic caption matcher) while still exercising the full layer-2 validator/interpreter/cache/UI pattern.
- **Scope:** ~2,000–4,000 LOC across the layers: `dsl.schema.json` + `validate_program.py` + `limits.py` (new op + arg domains + kind-flow + caps), `interpreter/primitives.py` (new `op_*` + `OPS` entry + diagnostic-empty semantics), the codegen op spec + few-shot example in `SYSTEM_PROMPT` (`api/codegen.py`), an eval-bank cell (`api/eval/question_bank.json`) with adversarial cases, and web rendering of the new step kind. **Budget note (verified):** `SYSTEM_PROMPT` is exactly 6694 chars against the ~6700 self-imposed ceiling — adding an op line + routing sentence + worked example *requires freeing headroom first*. ### 2. Codegen self-repair loop — close the layer-1↔2 cycle the single-shot path leaves open

- **Why now (verified):** `AzureCodegen.generate()` is strictly **single-shot** — confirmed: no `retry`/`repair`/`attempt` loop in `api/codegen.py`, and its docstring states *"there is no pinned fallback for a novel question."* On a validation miss the live path drops straight to honest-ungrounded. So a novel live query whose generated program trips `validate_program` (bad kind-flow, out-of-domain arg, over-cap step count) gets *no* recovery even when a one-line fix would have made it valid. That's the one open seam in the ViperGPT thesis this repo demonstrates: the execution layer already produces precise, structured validation errors — feeding them back to the LLM for a bounded repair attempt before falling back closes the generate→validate→repair cycle that the pattern is *about*. It's the highest-leverage robustness feature for the live/free-text path the gallery now puts front-and-center. Honest framing: the committed bank shows `T2_semantic_valid` 1.00 (42/42), so the *current* cases never exercise repair — which is exactly why this entry must ship **with** adversarial-invalid eval cases (queries that reliably induce an invalid first program) so the repair-rate is measured, not assumed.
- **Scope:** ~1,500–3,000 LOC: a repair loop in `api/codegen.py` (bounded retry budget, error-message → re-prompt shaping, give-up → existing ungrounded fallback), cost/latency guardrails (each retry is a billed Azure call — hard cap + telemetry), `api/server.py` wiring + a `repaired`/`attempts` field surfaced through the run record, an eval-bank slice of invalidity-inducing cases plus a new rubric tier or report column for repair-success, and (optionally) a UI affordance showing "repaired on attempt 2." Tests across the validate→repair→execute path.
- **Pipeline-ready:** ✅ — real design room: retry budget (1 vs N), how much validator detail to expose to the LLM vs. risk of error-message overfitting, whether to repair in-place or regenerate, idempotency/caching of repair attempts in `RunStore`, the give-up policy, and how to *measure* repair without contaminating the clean-program tiers. 5 agents would diverge meaningfully on the feedback-shaping and the eval design.
